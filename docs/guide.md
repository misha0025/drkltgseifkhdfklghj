# Репрайсер Wildberries и 1С:УТ 11

## 1. Назначение и границы

Репрайсер загружает каталог, цены учёта, остатки, продажи и плановые поставки из опубликованной типовой УТ 11. Для каждой позиции он рассчитывает предложение, объясняет причину и проверяет ограничения. Оператор может отклонить предложение, принять его в черновик или добавить свою цену. После проверки JSON пакет отправляется в имитатор Wildberries.

Это тестовый прототип. УТ используется на чтение. Изменения цен применяет локальный имитатор. Реальное соответствие идентификаторам WB, авторизация самой панели и интеграция с API Wildberries потребуются для пилота.

## 2. Быстрый запуск

Из корня репозитория, рядом с `app.py`:

```sh
docker compose up --build -d
docker compose ps
```

Откройте [127.0.0.1:3000](http://127.0.0.1:3000). Образ устанавливает данные часовых поясов и запускает приложение от непривилегированного пользователя. Состояние записывается в Docker-том `repricer-data`, путь в контейнере — `/data/state.json`. Остановка через `docker compose down` сохраняет том.

Compose публикует порт только на loopback хоста. Если Docker запущен на другой машине, откройте браузер там или из своего терминала подключите SSH-туннель:

```sh
ssh -N -L 3000:127.0.0.1:3000 user@server
```

После этого на своём компьютере откройте тот же адрес. Если ваш порт 3000 занят, укажите другой локальный порт туннеля, например `-L 13000:127.0.0.1:3000`, и откройте порт 13000.

### Без Docker

Нужен Python 3.10+ и системные данные часовых поясов для `Europe/Moscow`. Сторонних Python-зависимостей нет.

```sh
python3 app.py
```

По умолчанию Python-сервер слушает `127.0.0.1:8765`. Для запуска на порту 3000:

```sh
REPRICER_PORT=3000 python3 app.py
```

Параметры окружения:

- `REPRICER_HOST` — адрес прослушивания Python-сервера, по умолчанию `127.0.0.1`.
- `REPRICER_PORT` — порт Python-сервера, по умолчанию `8765`; в Compose установлено `3000`.
- `REPRICER_STATE` — путь к файлу состояния. По умолчанию используется `state.json` рядом с приложением. Родительский каталог должен существовать и быть доступен на запись.
- `REPRICER_1C_AUTH` — необязательное полное значение HTTP-заголовка `Authorization`. Используется только при отсутствии настроенного логина 1С.

Для чистого запуска рядом с действующим экземпляром:

```sh
REPRICER_PORT=8766 REPRICER_STATE=./state-demo.json python3 app.py
```

Без адреса учётной системы приложение загружает встроенные 60 товаров. В чистом состоянии с настройками по умолчанию 42 получают предложения. Отдельный процесс `python3 demo.py` нужен только для демонстрации JSON-источника и также использует порт 8766.

## 3. Работа в панели

### Товары

Поиск по названию, артикулу или внутреннему ключу и фильтры по категории и типу рекомендации применяются ко всему каталогу. Размер страницы — 15, 30 или 60 строк. В строке видны текущая цена WB, опорная цена, предложение, остаток, поставка и причина. «Расчёт» раскрывает продажи, дни наличия, темп, себестоимость и минимальную цену.

«Принять» добавляет рекомендацию в черновик. «Отклонить» помечает данное предложение отклонённым. Карандаш открывает ввод ручной цены. Черновик принадлежит текущей вкладке, сохраняется при её перезагрузке и позволяет хранить одну позицию на SKU.

Откройте «К отправке», проверьте цены и JSON, при необходимости уберите строки и нажмите «Подтвердить и отправить». После принятия задания цена ожидает ответа имитатора. При успехе обновляется текущая цена. После применения ручная цена также становится новой опорной. Статусы и причины остаются в истории. При отказе текущая цена сохраняется.

### Правила

Настройки задаются на категорию. По умолчанию повышение и снижение составляют 2%, отклонение от опорной цены ограничено 10%, интервал — 48 часов, пороги залежалости — 90 дней запаса или 30 дней без продаж. Для расчёта маржи исходно заданы 15% комиссии, 15% целевой маржи и 50 ₽ логистики на единицу.

В ручном режиме оператор подтверждает отправку. В автоматическом режиме сервер может сам отправить **новое** проходящее проверки предложение. Изменение режима само по себе не отправляет уже существующее предложение. В тестовом показе для наблюдения за JSON удобен ручной режим.

### Интеграции

Для подключения УТ заполните адрес публикации, логин, пароль при наличии, склад, организацию и вид цены. Названия последних трёх полей можно заменить GUID. Нажмите «Сохранить подключения», затем «Проверить соединения» и «Синхронизировать сейчас». Сохранение параметров и проверка не заменяют синхронизацию.

Ежедневное расписание работает в московском времени при запущенном сервере. Если сервер запустился после выбранного времени, он может выполнить пропущенный запуск за текущий день. После ошибки плановая попытка повторится в следующий день. Ручную синхронизацию можно вызвать отдельно. Панель показывает время последней успешной загрузки и последнюю ошибку.

Имитатор позволяет выбрать задержку от 1 до 60 секунд и порог максимального снижения. Снижение сверх заданного порога имитирует отказ площадки.

### Отчёт

Доступно сравнение двух окон по 7 или 30 дней. Продажи и отсутствие товара берутся из дневной истории. «Дни без остатка» суммируются по товарам. Маржа оценивается по текущей учётной цене, текущей себестоимости и настройкам расходов, взвешенным по продажам. Показатель залежалости использует текущий физический остаток и темп в соответствующем окне. Это оценка, поскольку исторические цены и историческая себестоимость для отчёта не сохраняются.

## 4. Интеграция с 1С

Стандартный OData публикуется на веб-сервере, а нужные объекты включаются в состав интерфейса. Адрес веб-клиента с окончанием `/ru/` поддерживается. Приложение нормализует его к `/odata/standard.odata`. Для подключения подходят HTTPS и HTTP, а при работе по сети HTTPS защищает учётные данные.

Необходимые объекты публикации:

- Справочники номенклатуры, характеристик, видов номенклатуры, складов, организаций, видов цен и валют.
- Справочники ключей аналитики учёта номенклатуры и учёта по партнёрам.
- Регистры накопления «Товары на складах», «Выручка и себестоимость продаж», «Себестоимость товаров», «Заказы поставщикам».
- Документ «Заказ поставщику» с табличной частью «Товары».
- Регистр цен «Цены номенклатуры» или «Цены номенклатуры 11.5», представленный в проверенной публикации как `ЦеныНоменклатуры25`.

Пользователю 1С достаточно прав чтения. Для начала проверки откройте `/odata/standard.odata/?$format=json` относительно корня публикации. Ответ `200` с пустым `value` означает, что вход прошёл, однако для этого пользователя отсутствуют доступные наборы данных. Проверьте состав публикации и права.

### Сопоставление данных

- **Ключ товара** — `ut:<GUID номенклатуры>[:<GUID характеристики>]`. Артикул показывается отдельно, так как он может повторяться. Категория определяется видом номенклатуры.
- **Каталог** — позиции выбранного склада с остатками, продажами либо поставками и с положительной рублёвой ценой базовой единицы выбранного вида цены. Если отдельной цены характеристики нет, используется базовая цена номенклатуры.
- **Наличие** — текущий физический остаток из `ВНаличииBalance`. Для рекомендации доступное количество равно физическому за вычетом `КОтгрузкеBalance`, с нижней границей ноль. Дневная история строится из начального остатка и движений за 60 завершённых дней. День считается днём наличия при положительном остатке в начале или конце дня либо при продаже.
- **Продажи** — движения регистра продаж по выбранному складу и организации. Аналитика связывает движение с номенклатурой, характеристикой и организацией. Возвраты уменьшают дневной объём, а результат за день ограничивается нулём снизу. Выделения отдельного канала WB в этом разрезе нет.
- **Себестоимость** — сумма управленческой стоимости и дополнительных расходов, делённая на количество в разделе «Товары на складах» по выбранной организации. При отсутствии положительной расчётной базы значение пустое.
- **Цена** — последнее действующее значение вида цены. Адаптер читает записи доступных регистров цен, так как вызов `SliceLast()` в проверенной базе возвращал ошибку.
- **Поставка** — положительный остаток к оформлению плюс остаток к поступлению. Привязка к строке идёт по ссылке заказа и коду строки. Отменённые строки, прошедшие даты и пустые даты не учитываются.

У заказа, который ещё не превратился в накладную, остаток может находиться в ресурсе «К оформлению». Поэтому для проверки поставки полезен пример частичного поступления по одному заказу.

Формат альтернативной JSON-выгрузки и дополнительные пояснения описаны в [руководстве по 1С](1c.md). Этот режим выбирается через API настроек для совместимости. Стандартная форма панели подключает опубликованную УТ через OData.

## 5. Алгоритм цен

1. Выбираются последние 30 завершённых дней. Темп равен сумме продаж, делённой на число дней наличия. Срок запаса равен доступному остатку, делённому на темп.
2. Оценивается тренд за две части по 15 дней. Для каждой требуется минимум 7 дней наличия. Рост больше чем на 50%, от 3 продаж за вторую половину и запас до 30 дней по новому темпу дают сигнал повышения. Падение больше чем на 35%, от 3 продаж за первую половину и запас от 45 дней дают сигнал снижения.
3. При нулевом доступном остатке цена сохраняется. Далее приоритет имеют цена ниже минимальной, дефицит до ближайшей поставки, рост или падение темпа, длительный запас и отсутствие продаж при устойчивом наличии. Правило отсутствия продаж требует минимум 10 единиц доступного остатка и установленное число дней наличия в окне.
4. Выбранное правило предлагает один фиксированный шаг категории. Проверяются допустимое отклонение от последней ручной цены, минимальный интервал, наличие задания по позиции и нижняя граница цены. Результат округляется до копеек.
5. Минимальная цена вычисляется по формуле `(себестоимость + логистика) / (1 − комиссия − целевая маржа)`. Комиссия и маржа подставляются долями. Недостающие данные блокируют расчёт. Шаг, который оставил бы цену ниже порога, блокируется целиком.

Пример. Продано 150 единиц за 15 дней наличия, доступно 30 единиц, поставка через 10 дней. Темп составляет 10 единиц в день, запас — 3 дня. При стартовой цене 1 000 ₽ и шаге 2% предложение составит 1 020 ₽, если пройдёт проверки.

## 6. Устройство проекта и API

- `app.py` — HTTP-сервер, синхронизация, расписание, проверка пакетов, отчёты и хранение состояния.
- `ut_odata.py` — чтение опубликованных объектов УТ и сбор снимка. Фильтры и пагинация применяются при запросах к OData.
- `engine.py` — расчёт рекомендаций на данных снимка, состояния цены и правил.
- `adapters.py` — транспорт к учётной системе и имитатор Wildberries.
- `demo.py` — встроенные и отдельно публикуемые демонстрационные данные.
- `static/` — интерфейс на HTML, CSS и JavaScript без отдельной сборки.
- `tests/` — приёмочные тесты, проверки OData-адаптера и сигналов алгоритма.

`GET /api/state` возвращает каталог с ценами и рекомендациями, правила, расписание, историю и отчёт. Пароль 1С в ответ не включается. `POST /api/action` принимает JSON до 64 КиБ. Успех возвращает `message` и обновлённый `state`, ошибки валидации — HTTP 400 с `error` и `state`.

| Действие | Поля и назначение |
| --- | --- |
| `settings` | `url`, `login`, `password`, `warehouse`, `organization`, `price_type`, `delay`, `max_drop`. Для старого JSON-источника явно передайте `mode: "json"` и при необходимости `service`. |
| `check`, `sync` | Проверить учётный источник или загрузить новый снимок. |
| `schedule` | `enabled` (логическое значение), `time` в формате `HH:MM`. |
| `rules` | `category`, `mode` (`manual` или `auto`), `up`, `down`, `margin`, `commission`, `logistics`, `deviation`, `interval`, `stale`, `idle`. |
| `approve`, `reject` | `sku`, `id` рекомендации. Основной интерфейс использует пакет для подтверждения. |
| `manual` | `sku`, `price`. Имитирует внешнюю ручную смену цены, которую затем подхватывает синхронизация. |
| `send_batch` | `task_id` и массив `items`. Для позиции передаются `sku`, `price`, `revision`, `source` (`manual` или `recommendation`) и `recommendation_id` для рекомендации. |

Повтор принятого задания с тем же идентификатором и содержимым возвращает успех без создания дубля. Другое содержимое под тем же идентификатором отклоняется. Перед постановкой в очередь сервер проверяет весь пакет, включая ревизии цен, актуальность рекомендаций и отсутствие ожидающих изменений. После принятия задания отдельные позиции могут получить разные результаты от имитатора.

## 7. Эксплуатация и диагностика

- **Страница не открывается.** Проверьте `docker compose ps` и `docker compose logs --tail=80 repricer`. При запуске без Docker проверьте сообщение сервера и выбранный порт. Помните, что `127.0.0.1` относится к компьютеру с браузером.
- **Порт 3000 занят.** Освободите порт или измените левый порт в привязке Compose, например `127.0.0.1:13000:3000`.
- **1С недоступна из Docker.** Исходящий запрос делается из контейнера. Проверьте, доступен ли адрес публикации из его сетевого окружения. Адрес `127.0.0.1` внутри контейнера относится к самому контейнеру.
- **401, 403, пустой OData.** Проверьте логин, пароль, права и состав публикации. Ошибка по конкретному ресурсу обычно указывает, какой объект проверить первым.
- **Нет товаров после проверки.** Сверьте склад и вид цены. Нужен положительный рублёвый прайс за базовую единицу. Если данные от сервера невалидны либо загрузка завершилась ошибкой, используется последний успешно загруженный снимок.
- **Товар есть, продаж нет.** Проверьте даты и проведение реализации, склад и организацию. Сохранённый черновик сам по себе в регистре продаж не отражается.
- **Нет предложения.** Откройте «Расчёт» и причину. Частые причины — отсутствие доступного остатка, недостающая себестоимость, короткий интервал или невозможность соблюсти ценовой порог одним шагом.
- **Пакет устарел.** Вернитесь в каталог, уберите устаревшую позицию из черновика и добавьте её заново по актуальным данным.
- **Резервная копия.** Для согласованной копии остановите экземпляр и сохраните файл состояния или содержимое тома. Файл содержит локальные настройки, историю и учётные данные 1С. При восстановлении используйте закрытый каталог и запускайте только один экземпляр с данным файлом.

## 8. Проверка и сценарий приёмки

```sh
python3 -m unittest discover -s tests -v
node --check static/app.js
docker compose config --quiet
```

Node.js нужен только для проверки синтаксиса фронтенда. Автотесты запускаются на изолированном состоянии и тестовых источниках. Для сквозной проверки используйте [сценарий демонстрации](demo.md).

Проверка на тестовой УТ дала 101 товар и 59 активных рекомендаций, около 58% каталога. Это результат конкретного снимка, а не заданная квота. На том срезе все активные предложения были на снижение. Повышение отдельно проверено на контролируемых данных. Из проведённой реализации загрузились продажи по 29 из первых 30 позиций. Дополнительный черновик реализации в расчёт не вошёл.

## 9. Перед пилотом

Потребуются отдельные учётные данные 1С на чтение, защищённый доступ к веб-панели, база данных для состояния и заданий, мониторинг свежести снимков и отказов, а также адаптер реального WB. Для реального применения отдельно проверяются соответствие товаров и характеристик карточкам площадки, ограничения API, повторные попытки и сверка фактически применённых цен.
